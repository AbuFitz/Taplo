# Audit and editor-tool decision (direction change 2)

Written before any code changed. Observations are from the repository at commit `5fed1e3`, not from the earlier plan.

**Spec file:** `TAPLO-CLAUDE-CODE-SPEC.md` is **not in the repository** (nor anywhere on the build machine); it was only ever supplied in chat. `docs/product-decisions.md`, `docs/theme-engine.md` and `docs/implementation-status.md` have been the working record. `docs/spec-direction-2.md` lists exactly which clauses this direction supersedes.

## 1. What exists today

### Systems
| Concern | Reality |
|---|---|
| Layout | 5 "layout families" (`presets/layouts`), each a fixed ordered list of 10 *block* types with a hard-coded variant per block. |
| Theme/tokens | 5 token presets, one per family, referenced by `layout.tokenPresetId`. Internal token model: 7 colours, 2 fonts, width, spacing, radius, shadow, motion. |
| Blocks | Website *sections* (`Section` wrappers with 3–7.5rem vertical padding, big heroes, 4xl headings). Not compact widgets. Visibility = "has content"; there is no instance model: one of each, fixed by the layout. |
| Industry | 45 presets: terminology, suggested services, `defaultLayoutId`. **Industry → layout → tokens is one fused chain**, so industry *does* determine visual identity. |
| Widgets | None. "Block" is not an addable/duplicable/configurable unit. |

### Owner controls actually exposed
Layout switch (5 cards), accent colour, heading font (Core+). Nothing else. Section order/hide is implemented in `view-model.ts` (`config.sections`) but **no UI writes it**.

### Capabilities that exist only in schemas/rendering code
- `overrides` accepts `background, foreground, accentForeground, bodyFont, radius` — UI never sets them.
- `config.sections` ordering/hiding (above).
- `tokens.motion`, `shadow`, `sectionSpacing`, `contentWidth` — fixed per preset, not owner-editable.
- Image refs have `width/height` but no crop/focal point; there is no upload path at all.
- Hero background, header arrangement, button/card style: not modelled.

### Storage
- Business data (`BusinessContent`) and presentation (`config`) are separate objects in `draft`/`published` — good, kept.
- `config = {schemaVersion:1, layoutId, layoutVersion, tokenPresetId, overrides{7 keys}, sections?}`.
- Demo: `localStorage` key `taplo.demo.v1` → `{content, config, plan, published{content,config,plan}}`. SQL: `profile_drafts`/`profile_versions` hold `content`+`config` JSONB (schema-agnostic, so a new config shape needs no table change, only a `schema_version` bump).

### Preview vs published
Same `buildPublicProfileViewModel` + `ProfileRenderer` for the editor preview (`/demo/preview` iframe), the published demo page, the fixture routes and the real public route. This is the right architecture and is preserved.

### Libraries: installed vs actually used
| Package | Used by app code? |
|---|---|
| next, react, tailwindcss, radix-ui (via shadcn), zod, lucide-react, cva, cn, @fontsource/* | yes |
| @supabase/supabase-js | yes (one file: public RPC client; not exercised against a live project) |
| **react-hook-form** | **no — installed, zero imports** (forms are controlled-state) |
| **@supabase/ssr** | **no — installed, zero imports** |
| **date-fns, react-day-picker** | **no** (calendar component generated by shadcn, unused) |
| shadcn components unused by app code | calendar, table, tooltip, dropdown-menu, avatar, alert, skeleton, switch, popover, separator |
| dnd-kit / Puck | not installed |

Action: remove `react-hook-form`, `@supabase/ssr` until used; keep shadcn primitives we will use (switch, dropdown-menu, tooltip, popover, avatar, slider additions).

### Honest assessment
The "five layout families" were five website templates with a recolour: structurally the same long-scroll sequence of marketing sections, bound to industry. This is the thing to replace, not extend.

## 2. Editor-tool research

Sources: npm registry metadata (queried today), official docs at dndkit.com / docs.dndkit.com, puckeditor.com/docs, the `puckeditor/puck` README. **Gaps are stated, not papered over.**

### A. Custom editor on dnd-kit
- **Packages:** stable `@dnd-kit/core 6.3.1` + `@dnd-kit/sortable 10.0.0` (MIT, React ≥16.8, last published Dec 2024) and a newer rewrite `@dnd-kit/react 0.5.1` / `@dnd-kit/dom` (**pre-1.0**, published 2026-10-15). The official docs now label the core/sortable pages "Legacy".
- **Interface freedom:** total — it is only drag infrastructure; we render everything.
- **Touch:** `TouchSensor` with delay + tolerance (docs example: 250 ms / 5 px); `MouseSensor` distance constraint; handles are supported via activator node ref so only the grip drags (page still scrolls by touch).
- **Keyboard:** `KeyboardSensor` + `sortableKeyboardCoordinates` (Space/Enter pick up, arrows move to the neighbouring item, Space/Enter drop, Esc cancel); customisable `screenReaderInstructions` and live announcements; focus restoration after keyboard drags.
- **Live preview / fields / undo / serialization / migrations:** all ours — which is the point, because they must bind to Taplo's domain model (widgets referencing business records, entitlements, validated config).
- **Cost:** we must build the widget list, add/edit UI, history and form generator. dnd-kit gives none of it.
- **Licence/cost:** MIT, no paid tier.

### B. Puck
- **Package state:** core is MIT; the npm package was renamed — docs/README now say `@puckeditor/core`, while `@measured/puck 0.20.2` (Jan 2026) is the old name and `@puckeditor/puck` does not exist on the registry. Two names → churn risk.
- **Fit:** component `config` with `fields` → props; render functions; Root config; categories; dynamic props/fields; read-only props; **viewports in a same-origin iframe**; permissions (toggle duplicate/delete); history API (`back/forward/hasPast/hasFuture/histories`, injectable history); `onPublish`/`onAction`.
- **Interface freedom:** `overrides` can replace header, outline, drawer, fields, preview, action bar, etc. — but the docs state the overrides API **"is highly experimental and is likely to experience breaking changes"**, and per-override prop contracts are not on the overview page.
- **Not verified from official docs:** touch/mobile editing and keyboard-accessible reordering (not mentioned in README or overview; the repo shows 172 open issues I did not triage). For a product whose owners edit *on phones*, "undocumented" is a risk we would have to test ourselves.
- **Data model:** Puck owns the document shape (`content` + `root` + `zones`, component ids). Our model is different (ordered widget instances bound to business records, per-widget appearance overrides, entitlement filtering, demo store/SQL snapshots). We would either map two representations or bend ours to Puck's.
- **Paid:** core MIT; "Puck AI" and Cloud are separate paid products (not wanted).

### Why not Craft.js or GrapesJS
- **Craft.js** (`0.2.12`, pre-1.0, last published Feb 2025): a React node-tree/free-canvas framework — good for arbitrary nested layout, but Taplo pages are a *flat ordered list of typed widgets*; its node/serialization model and inactivity add cost without benefit.
- **GrapesJS** (BSD-3, active): a framework-agnostic HTML/CSS web-page builder whose model is arbitrary HTML and CSS. That is the opposite of "validated configuration + trusted components, no owner-authored CSS/HTML", and it would not render our React widgets natively.
- (Based on registry metadata and the libraries' published design; not re-read from their docs today since neither is a candidate.)

### Comparison against the requirements
| Requirement | dnd-kit (custom) | Puck |
|---|---|---|
| Fully custom owner UI ("plain language", no technical names) | ✅ native | ⚠️ via experimental overrides |
| Mobile/touch | ✅ documented sensors/handles; we test | ❓ undocumented |
| Keyboard reordering + announcements | ✅ documented | ❓ undocumented |
| Live preview | ✅ ours: same renderer, iframe | ✅ built-in viewport iframe |
| Configurable widget fields | build a small field generator (~200 lines) | ✅ built-in |
| Global + per-widget appearance | ✅ our schema | custom fields only |
| Serialization/migrations | ✅ our zod schemas + `migrate()` | Puck data + our migration of it |
| Undo/redo | build (snapshot stack, ~80 lines) | ✅ built-in |
| Widgets bound to business records, entitlements | ✅ natural | needs data adapters |
| Maintenance risk | 2 stable MIT packages | rename + experimental overrides |

## 3. Decision

**Custom Taplo editor on `@dnd-kit/core` + `@dnd-kit/sortable` + `@dnd-kit/utilities`**, retaining Next.js, TypeScript, Tailwind, Radix-based shadcn/ui and zod.

Reasons: (1) the owner experience *is* the product and must be bespoke, accessible and phone-first; (2) our document is a flat typed widget list tightly bound to business records and entitlements, which is cheaper to edit directly than to adapt; (3) Puck's strongest assets (field generator, history) are each small to build, while its weakest points for us (mobile/a11y unverified, experimental overrides, package rename) hit our core requirements; (4) we keep one schema and one renderer for preview and published.

**Why the stable packages, not `@dnd-kit/react 0.5.1`:** the rewrite is pre-1.0; the documented keyboard/touch/handle behaviour I verified is for `core`/`sortable`. Revisit when `@dnd-kit/react` reaches 1.0.

Not installed: Puck, Craft.js, GrapesJS. No paid dependency.

### Risks and how they are tested
- Touch drag on phones → Playwright touch-event drag + mandatory move-up/down buttons as the accessible alternative.
- Keyboard drag → Playwright Space/Arrow/Space on the handle.
- Pre-existing `dnd-kit` React 19 peers → peer range is `>=16.8`; verified by build + e2e.
