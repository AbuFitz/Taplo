# Taplo · Easy setup and low avoidable support demand

Working edition 2.8 · 3 November 2026. Adopt these rules as feature requirements, not a support-minutes cap imposed on customers. Current 5/10/20-minute support assumptions remain hypotheses; do not deny essential help to make a model look profitable.

## Owner journey and guidance

Start with business identity, chosen look and useful intended actions; account at end. Enter Studio with the real draft and a single Next useful action based on capability dependencies. No registration form collecting every future operating fact. A recognisable draft is different from a published transaction-ready business. Make Save draft/Preview/Publish explicit. Choose a relevant example without inventing owner prices, hours, logo initials or legal facts.

Today surfaces urgent accepted work first, then the next incomplete dependency. A new merchant sees Set up your first service/product/session, not fake analytics. Guide where the task happens. A checklist is optional progress navigation, not a permanent dashboard of guilt. Skip hides a suggestion without making a required dependency true. Completed state derives from current records/readiness, never a checked UI flag.

## Quick setup by task

| Task | In-place minimum | More settings / handover | Do not do |
| --- | --- | --- | --- |
| First service | Title, explicit owner price mode/value, duration, bookable resource | Eligible staff, buffers, policy and intake | Guess price/duration or send owner through five disconnected pages |
| Working time | Exact resource/location/timezone, weekday intervals, effect date and impact | Breaks, exceptions, complex shifts | Confuse public opening hours with bookable time |
| Physical product | Name, explicit price, image optional, variant/stock mode and fulfilment | Full variants, stock ledger, delivery/returns | Imply Add product also makes shipping/tax ready |
| Class | Date/timezone, seats, host/resource and price | Course/series/waitlist/participant rules | Count payers as seats or infer room capacity |
| Quote-led work | Scope, request questions, response expectation | Variations, quote acceptance and scheduling | Treat enquiry as confirmed work or accept price on customer's behalf |
| Team | Person/resource choice, offer/location assignment and access summary | Deliberate invitation/role review | Grant financial access through an innocuous staff toggle |
| Deposit | Amount/mode, customer review and reviewed policy summary | Stripe readiness/provider onboarding | Mark payments ready after choosing a percentage |
| Collection/delivery | Suitable location/zone, lead time and actual cost | Capacity/tax/exception settings | Reuse staff hours or silently add checkout costs |
| Rewards | Earn rule, reward, threshold and live preview | Funding, refund/expiry/redemption rules | Default every category into a generic stamp programme |
| Calendar | Which calendar/direction and privacy summary | Real OAuth and resume/verification | Display connected after a button click |
| Messages | Operational template/time/channel or draft eligible campaign | Sender, consent and cost review | Add marketing to receipts or dispatch on save |
| Domain/Wallet/NFC | Destination/identity preview and next required step | Real provider/phone verification | Call preview issued/installed/connected |

Quick save and full editor share record/version/validator/permissions; unshown fields remain. One focused task surface, no nested modal chain. The service draft remains intact when working hours save. Give More availability settings after the quick task, not mandatory navigation before finishing it. With complex inherited rules, show what is controlling the outcome and open exact full scope safely; never flatten it into a simpler shadow data model.

## Visual and interaction contract

Mobile task canvas has readable text, persistent context, keyboard-safe final action, 44px minimum targets and explicit close/back. Desktop uses the current task canvas or a focused neutral modal when necessary, not a universal tacky side panel. At 200% zoom, important facts and actions remain reachable. Busy states name the operation and retain values. Destructive changes need impact review. Errors attach to the field/action that can fix them; retain work after timeout/conflict.

Optional short demonstration can show a real interaction/illustration at the moment it helps, muted and controllable, respecting reduced motion/data. No unsolicited floating autoplay video, repeated tour on every visit, blocking confetti or hard-to-dismiss guide. One-time coach marks never cover the target or contain the only accessible explanation. Clear inline examples beat animation when the field is self-explanatory.

## Prevent support before a ticket is needed

Use explicit readiness states per capability: not_started, draft_incomplete, action_required, verification_pending, ready, temporarily_unavailable, restricted. A single account connected boolean is insufficient. Distinguish a merchant's missing setup from provider outage, permission denial, billing restriction and data conflict. Show one next action and preserve context on external return. Always re-fetch provider truth before unlocking a function.

| Symptom | Self-service resolution | Human/Console route |
| --- | --- | --- |
| No slots | Explain actual constraint: hours/resource/lead time/busy/coverage, scoped to role | Support receives diagnostic codes and relevant revisions, not private calendar payloads |
| Can't take payment | Show verified charge/payout requirements separately; resume provider setup | Financial case with operation/account reference, never ask for passwords/card details |
| Unknown booking/refund result | Checking outcome; retry status using same operation ID | Reconcile authoritative result, no manual duplicate charge/refund |
| Domain not live | Actual DNS/ownership/certificate stage and safe relevant records | Escalate without replacing MX or unrelated DNS |
| Message not sent | Purpose/suppression/sender/quota/queue state and permitted fix | Abuse/delivery case with redacted recipient/context |
| Can't find reward | Correct programme/holder/eligibility; explanation of rules | Adjustment review by permitted role, no arbitrary balance edit |
| Staff sees wrong work | Active business and permission summary, safe switch | Owner grant/invite review; no expose-all troubleshooting toggle |

Help starts with task context and relevant short answer; customer can still contact a human. Support request automatically attaches permitted request/operation ID, product/build, entity IDs, error code and relevant setup stage after showing what is included. Exclude credentials, full payment details, clinical notes and unnecessary addresses. A diagnostic bundle does not authorise support to impersonate/refund/publish. Explain who owns the next step and show a persistent case timeline instead of a lost chat popup.

## Operating measures and cost feedback

Measure task completion/correction, setup abandonment at actual step, support contacts per activated merchant, repeated errors, resolution time, reopening and owner/customer satisfaction. Segment by capability/team/category/device; avoid an average hiding one unusable path. Use privacy-safe event IDs and coarse timing, not sensitive session recordings. Fix recurring causes before buying more chat automation. Help automation drafts/classifies/suggests; consequential financial/ownership/moderation decisions retain explicit human authority.

Working design targets for first observation: owner can identify the next action without explanation; no re-entry of known data; no loss on back/keyboard/provider return; accurate understanding before publish/payment; usable recovery with context. Time targets are experiment hypotheses, not claims of measured usability. Actual observation protocol is in INTEGRATION-AND-OPERATING-EVIDENCE-PACK.md.
