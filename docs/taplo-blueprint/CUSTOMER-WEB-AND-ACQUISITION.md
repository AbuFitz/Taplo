## One customer service in app and browser

Yes: customers can use Taplo in a normal mobile or desktop browser. Core browse, booking, shopping, payment, cancellation/refund tracking, saved-business and private-return tasks must not require installing an app. Native app adds a convenient returning destination, platform-appropriate notifications and supported device functions; it is not a gate around ordinary customer service.

Use Taplo as the customer-facing name and Taplo Studio for owners. A separate consumer brand is not needed to explain this. Console remains a restricted operating environment. ## Responsive compositions

Mobile Explore: location/manual search → one search field → compact category filters → useful result groups/list; map is an intentional toggle with the same query/results. Four destinations Explore/Saved/Activity/Account use a restrained bottom navigation on global customer views. Business page retains its own block composition, with small contextual back control when arriving from Explore/Saved. Checkout replaces browsing navigation with task controls. No duplicated Home/Discover/Feed tabs.

Desktop Explore: search/results beside a map when selected; a result and its selected marker remain synchronised. Business mini-spaces retain a compact deliberate width, not a stretched conventional website. An expanded task can use a clearly contrasting surface beside/over its origin while retaining a direct route. Activity has an accessible list and selected detail; no dense mobile cards blindly scaled up to desktop.

Guest can browse and transact where supported. Saving or seeing private activity needs authenticated identity, with return to the exact task afterwards. Existing guest transaction links grant narrow verified access, not an entire customer account or another family member's history. Sign-out clears private cached content; public pages can cache separately. Offline views must label cached status and never imply a newly confirmed payment/booking without server evidence.

Required state designs: no results, manual town, denied geolocation, map unavailable, missing image/logo, unavailable merchant, removed offer, private sign-in return, expired guest link, unavailable app region/device, pending payment and restricted page with existing-customer support access. These are design requirements; final populated mobile/desktop/light/dark captures are still to be produced.

## App promotion with a reason

Prompts are contextual: after a completed booking/order, after a customer saves a second business, or on a deliberate App page visit. No install interstitial before paying, cancellation, reporting, reading a refund or essential legal information. No compulsory phone number or marketing opt-in to get the app.

Proposed confirmation card: **Your booking is confirmed. Keep your appointments and favourite businesses together in Taplo.** Actions: Get the app; Continue here. Booking confirmation remains above it. Merchant identity is not replaced by a giant Taplo advert. One clearly dismissible optional card, not native banner + floating popup + download footer competing on the same screen. Remember dismissal through appropriate minimal storage; frequency policy begins at one custom prompt per 30 days/device where lawful persistence works, never fingerprint someone to enforce it.

Apple documents a platform Smart App Banner [W1]; use it where supported with real App Store ID. Android app opening uses verified App Links [W2], with deliberate web/store fallback. App identifiers, signed association files, production hosts and supported paths must match. Merchant custom domains do not automatically become verified app links. Their Open in Taplo route can navigate through a verified Taplo HTTPS host without forwarding private bearer tokens.

Do not promise seamless post-install task restoration without a proven mechanism. Public business/offer context can be a safe resume reference; private activity requires authentication and access checks in the app. Never embed payment secrets or private booking credentials in a QR/store campaign URL. GET/HEAD/unfurl cannot consume tokens, accept terms, cancel or charge. Repeated store/deep-link taps must not duplicate a commitment.

Desktop App page may show a sharp QR to the public /app route plus labelled store buttons. Prefer device-appropriate options without preventing manual platform selection. Missing/unavailable store listing gets a truthful fallback; never fabricate download counts, ratings or non-working badges. Browser install/PWA and native store install are distinct actions, not one misleading Download button.

## Database clarification

Neon Postgres is the current working database direction; this is not an instruction to rip out a functioning Supabase implementation. Both providers now advertise broader backend capabilities. Supabase bundles Postgres/auth/storage/realtime; current Neon also advertises managed Better Auth, object storage, functions and beta realtime. Taplo still needs an explicit supported choice for each role, actual region/security/backup/permission configuration and measured cost, regardless of advertised bundle. PROVIDER-STACK supplies those initial choices/candidates. Inventory actual repository dependencies and select/migrate with evidence before changing infrastructure. No clinical/child-data suitability is established simply by choosing either brand.
