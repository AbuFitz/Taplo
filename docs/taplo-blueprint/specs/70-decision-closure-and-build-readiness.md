# 70 · Decision closure and build readiness

Edition 1.0 · This pack deepens four areas; it does not declare the entire platform finished or promise only minor research changes.

## Where the edition is concrete

- Visual baseline: tokens, component recipes and designed reference screens in addition to region schematics.
- Operating profiles: tutoring, mobile services, retail and workshops with setup, availability, customer action, daily work and exceptions.
- Engineering: typed core record schemas, role/action sets, guarded lifecycle graphs, command input schemas and integration recovery rules.
- Commercial/operations: candidate seller/payment model, cost formulas, packaging/allowance rules, support responsibility, import and exit lifecycle.
- Team: merchant-scoped shareable professional profile and login, with controlled appearance/editing and explicit independent-operator distinction.

## Decisions that require actual evidence/authority

| Decision | Current recommendation | What closes it |
| --- | --- | --- |
| Final brand visual system | Neutral frameless shell; independent merchant palettes | Founder/design review of complete core journeys |
| First launch segment/scope | Evaluate a connected goods+scheduled-work pilot alongside service/quote use | Access to operators, observed need, delivery/support feasibility |
| Payment/risk allocation | Merchant-led sale; evaluate suitable direct-charge Connect configuration | Provider agreement/availability and qualified legal/tax review |
| Price/allowances | Base subscription + explicit cost-bearing extras | Supplier quotes, cost scenarios, demand evidence |
| Team independent sellers | Distinct seller/payment boundary from an employee profile | Actual operating relationship and chosen commercial scope |
| Support promises | Defined case ownership; targets aligned to staffing | Named responsible team, runbooks and actual capacity |
| Data/retention/category policies | Purpose-limited fields and versioned policies | Reviewed supported scope and implemented access/lifecycle |
| User usability | Pre-session walkthroughs then independent task observation | Actual observations, not generated personas or internal simulation |

These are not recurring permission prompts for ordinary design/build work. Continue reversible implementation within authorised scope; do not publish contractual promises, purchase services or misrepresent unapproved obligations. Record proposed versus approved decisions in one current register.

## Build handoff checklist

A builder should identify the command and source record for each screen action; its actor/field permissions; exact required input; guard/conflict outcome; authoritative status; associated owner/customer/support projection; theme/composition rules; and external operation/recovery. The contract artifacts are an initial baseline and must be extended for referenced contact/assets/policy/offer configuration records and additional feature families. Do not hide undefined behaviour behind an untyped generic configuration object.

The designed references cover selected screens. Full map UI, all checkout states, all category editors, actual native handovers and every component variant remain explicit design work. Real provider/device testing and user observation are not replaceable by another paragraph. Complete a connected implementation increment and preserve the wider vision in the backlog without advertising all proposed capabilities as shipping.

## Honest completion language

“Specified” means a decision/rule is documented. “Designed reference” means a populated visual exists. “Contract validated” means syntax/reference/fixture checks passed, not that concurrency or security is implemented. “Connected” means actual end-to-end integration evidence. “User validated” requires real observed people. Keep these evidence labels internal; public wording naturally describes the intended service and only claims available capabilities appropriately.
