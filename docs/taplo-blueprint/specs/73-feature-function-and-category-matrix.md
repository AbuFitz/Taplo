# 73 · Feature, function and category matrix

Edition 1.0 · Function catalogue and applicability map. It is not a claim every category-specific feature is researched, implemented or committed for launch. Detailed four-profile contracts are in 62; team access is in 72.

## Functions, not just menu labels

| Feature family | Actual function | Scope / dependencies | Important exception |
| --- | --- | --- | --- |
| Business identity | Store authored trading name, assets and context | Merchant plus public projection | No artwork/name duplication or invented initials |
| Blocks/composition | Present the same offers through compact widgets | Page version and merchant theme | Source edits do not duplicate catalogue/inventory |
| Appearance | Coordinated look, safe accents, scoped overrides | Page/block/popup; personal app theme separate | Reset/inheritance and contrast |
| Public routes/SEO | Crawlable canonical business/item/profile facts | Published eligible records and host mapping | Private data never indexed |
| Explore/list | Match intent to eligible merchants/offers | Search projection, area, capability | No invented availability/popularity |

| Reviews | Eligible experience feedback | Subject/moderation/fraud rules | No copied business rating on staff profile |

| Domains | Connect/buy/verify/renew/exit hostname | Ownership/provider/DNS/registration | Order accepted ≠ active mapping |
| Analytics | Explain useful operational/conversion outcomes | Event definitions/privacy/scope | Pending payment ≠ revenue |

| Imports/exports | Guided authorised migration | Provenance/schema/secure files | No implied consent or transferable mandates |
| Billing/allowances | Sell software and meter agreed usage | Cost model/terms/entitlements | Preserve existing paid customer commitments |
| Closure/offboarding | Wind down access and outstanding obligations | Work, finance, domain/NFC/pass plan | Closure ≠ destroy every historical record |

## Applicability by operating model

“Core” below means a likely useful capability for this reference model, not a compulsory signup step. Optional capabilities can be added. A feature outside the four deep profiles needs its own domain walkthrough before being enabled.

| Operating model | Likely core | Optional additions | Team/work emphasis | Distinct rule still required |
| --- | --- | --- | --- | --- |
| Barber/beauty | Appointments, professional profiles, calendar, reminders | Retail, rewards, deposits, packages | Own calendar versus front desk/team management | Named professional, staff price/time, chair/resource and seller identity |
| Tutor/coach | Lessons, participants, staff, recurrence, private messages | Groups, credits, memberships | Assigned learners/reports | Payer/learner, joining privacy, attendance/chargeability |
| Mobile repair/detailing | Coverage/intake, quote or appointment, jobs | Parts/goods, deposits, gallery | Assigned technician/jobs/travel | Address/travel, scope changes and compatibility |
| Retail/maker | Catalogue/variants, inventory, orders, delivery/collection | Workshops, rewards, commissions | Preparation/collection/stock roles | Stock race, partial fulfilment and return disposition |
| Workshop/event host | Dated sessions, capacity, roster | Waitlist, courses, materials sales | Instructor/host/check-in | Seats/resources, occurrence/course distinction, cancellation |
| Photographer/creative | Portfolio, enquiry/quote, dates | Deposits, packages, products | Assigned shoot/project and deliverable access | Usage rights, delivery acceptance and private galleries need separate contract |
| Consultant/professional | Service menu, enquiry/appointment | Retainers, documents, recurring work | Assigned case/project visibility | Confidentiality and professional-scope policy before implementation |
| Fitness/training | Private/group sessions, capacity/resources | Credits, membership, rewards | Instructor/coach/roster | Health/support information and eligibility need restricted-purpose design |
| Vehicle seller | Stock listings, enquiries, viewings | Deposits, accessories | Stock/lead/viewing assignment | Unique-item reservation, finance/sale obligations not defined by generic checkout |
| Food/coffee | Menu/info, selected goods, rewards | Preorder/collection, classes | Preparation/collection | Allergen, perishability and timed fulfilment require dedicated reviewed rules |
| Personal brand/creator | Identity, media, links, enquiry | Services, eligible goods, memberships | Often solo; optional collaborators | Digital-content/recurring supply rules need deliberate contract |
| Mixed business | Any deliberately enabled supported capabilities | Incremental expansion | Role/task navigation adapts | One identity; distinct inventory/time/entitlement and agreements |

## How to expand correctly

For each new model, specify source records; required and optional setup; eligibility; customer action/commitment; owner/staff task; exception/refund; public/private data; platform/payment responsibilities; mobile/desktop/theme frames; actual providers; and acceptance scenarios. Do not equate a checklist row with a researched specialist workflow. Capture unknowns visibly and keep unsupported commitments disabled while presentation/enquiry can remain useful.

## Depth clarification · 1.3

Spec 91 is the explicit category completion map. Neither this applicability table nor a category-specific label/icon means all specialist workflows are specified. Unsupported commitments must not be advertised/enabled merely because a category appears in onboarding.
