# 94 · Blueprint as an agent and operating contract

Working edition 1.4 · 3 November 2026 · Process design for the entire Taplo plan. The objective is a connected, reviewable platform specification across product, design, engineering and operations. No claim of exhaustive completeness or statistically established near-perfect correctness.

## A living specification, not an accumulating pile of chapters

Deepen existing requirements in place when their meaning changes; add focused references where necessary. Every change needs a dependency review across customer, Studio, Console, records, permissions, communication, integrations, commercial and legal effects. A new document does not by itself close an old gap. A coverage matrix remains the current index of what exists and what is still unresolved.

Each feature has a stable identifier, purpose, supported categories/capabilities, owner and revision. Distinguish founder direction, product recommendation, primary-source finding, approved decision, designed reference, typed contract, implemented result and verified outcome. Those states are independent; more prose cannot promote a feature from proposed to tested.

## Required feature packet

| Dimension | Required content |
| --- | --- |
| Purpose and boundaries | User problem/outcome, supported scope, non-goals and dependencies |
| Actors and authority | Owner/staff/customer/participant/support actions, tenant/field rules and authentication |
| Setup | Defaults, deliberate choices, quick/full editors, readiness and progressive guidance |
| Behaviour | Normal path, changes/cancellation, lifecycle transitions, guard conditions, time/stock/money effects |
| Data/commands | Exact types, IDs, nullability, server authority, versioning, invariants and migration |
| UX/UI | Mobile/desktop layout, components/tokens/icons/type, interaction, copy and all material states |
| Integrations | Supplier/mode/scopes, callback/retry/reconcile/disconnect, cost/limits and exit |
| Communication | Purpose/recipient/channel/trigger, consent, template/version and failure handling |
| Operations/compliance | Console authority/runbook, seller/data responsibilities, retention and applicable review |
| Verification | Normal/adversarial/failure/concurrency cases, expected result and evidence |
| Traceability | Related feature/decision/source/schema/screen/scenario IDs and unresolved items |

Apply this packet to small capabilities as well as headlines: refund button, role grant, hours copy action, logo crop, message resend, domain renew and guidance dismissal. Depth should follow consequence; not every cosmetic decision needs a legal essay, and no financial action can rely on a pretty screenshot alone.

## Source precedence and conflict handling

Latest explicit founder direction takes precedence over stale product choices within the authorised scope. Enforced legal/provider obligations still require correct handling and explanation, not silent violation. Current approved decision and its linked specification govern; machine contracts and screens must be reconciled to match. Historical research/mockups are evidence/context, not implicit approval. The pack needs a decision/source map rather than an agent guessing that the newest filename always wins.

If a feature packet contains a conflict, the agent records the contradiction and resolves routine reversible details with documented rationale. Escalate only consequential ambiguity needing actual business/provider/legal authority. Do not invent prices, privacy bases, sender verification, supported categories or a payment guarantee to fill a gap. Block the affected commitment while continuing independent authorised documentation/design work.

## Agent task envelope

Each handover supplies: task/feature IDs; blueprint revision; exact relevant specs/contracts/decisions; desired outcome; in/out of scope; permitted changes; upstream prerequisites; interfaces/fixtures; UX/copy requirements; risk/failure cases; validation; deliverables and unresolved assumptions. A coding task should not force the implementer to invent the seller model or refund policy. A design task should not leave focus/back/error/loading and financial disclosure to interpretation.

Agents return changed requirement IDs, decisions made, files/screens/contracts affected, tests/review evidence and unresolved conflicts. No self-awarded complete badge. Review the connected result rather than accepting a list of components. Tests that merely mirror implementation do not establish the underlying requirement is right.

## Console is governed by the plan, not granted unlimited power

Console help/runbooks may use a curated current subset of the blueprint. Actual operator access/actions remain enforced by server roles, command guards and audit. Never let a retrieved document, customer message or AI-generated suggestion grant financial/admin authority. External/user content is untrusted evidence. An assistant may explain a refund case; execution still needs the permitted human/system action and validated state.

Documentation for Console requires role-safe retrieval, source revision, clear recommendation-versus-policy distinction and redaction. Customer private information must not be copied into a global knowledge corpus. Product documentation updates do not retroactively rewrite accepted agreements or enable new Console powers.

## Change and release process

Record proposed change → assess dependency impact → revise canonical requirements/decisions → reconcile affected design/contracts → independent critique and scenario rehearsal → build a connected increment → verify against requirements → update evidence/remaining gaps. Research and design continue to revise the plan when needed. This process does not require pre-approval for ordinary reversible blueprint improvement.

For each change inspect access/privacy, concurrency, money/time/stock, category variation, origin/return context, notification schedule, migration/exit and provider failure. Maintain trace links so changing one rule reveals affected screens, messages, tests and support actions. A plain-text cross-reference is a starting point; automated trace verification is future tooling until actually built and run.

## Reliability and the near-perfect objective

Use explicit invariants and measurable failure budgets where they make sense: no duplicate captured payment from a repeated action; no cross-tenant data access; no accepted capacity overcommit under the defined model; no unsupported successful delivery claims. Verify with scenario, property/concurrency, security and recovery evidence appropriate to each feature. Set availability/recovery targets only against a specified service boundary, operating capacity and measured system.

99.99999% correctness has no defensible meaning without a defined population of actions, failure definition, observation window and evidence. More planning improves clarity but can also preserve a mistaken assumption at greater length. Aim for exhaustive reasoning about known critical cases, clear unknowns, independent review and controlled change. Real users/providers/devices expose information that the written plan cannot establish beforehand.

## Priority deepening queue

1. Bring one complete setup-to-customer-task-to-support journey to feature-packet depth, including visuals and exact contracts—not only new headings.
2. Complete each category's distinct rules using 91's matrix; shared patterns reduce duplication but do not erase specialist responsibilities.
3. Reconcile proposed policy/authority/notification/guidance records with typed schemas and action permissions.
4. Complete screen/component/state coverage, asset/icon/font manifest and actual mobile/desktop interactions.
5. Verify provider choices, commercial/support capacity and applicable legal decisions; retain remaining broader ecosystem work without advertising it as released.

This edition deepens guidance/process specifically. It does not claim every existing chapter has already been brought to that standard.

## Founder delegation and manageable passes · 1.5

The founder supplies ideas freely and delegates synthesis, independent thinking and routine blueprint decisions. Recommendations become documented working defaults unless superseded; do not end work waiting for approval of reversible documentation/design choices. Break a broad input into connected passes and finish a concrete reviewable increment each pass. Explain consequential tradeoffs concisely; keep the full reasoning in the blueprint. Do not respond to broad scope by merely adding headings or promising unseen work between turns.

Exact external/provider/legal approvals cannot be fabricated. Defaults may be chosen for design exploration while evidence/eligibility is tracked separately. Refer to 95 for tools/workflow and 96 for quick-setup breadth; scope changes require updating the affected existing contracts rather than appending contradictory suggestions.
