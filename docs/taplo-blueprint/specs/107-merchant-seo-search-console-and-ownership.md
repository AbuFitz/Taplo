# 107 · Merchant SEO, Search Console and ownership

Working edition 2.0 · 3 November 2026 · Adopted UK-first public-page SEO and owner-guidance design extending 36, 40, 84 and 105–106. Current Google primary-source checks inform this contract. No Search Console property, OAuth connection or live verification was created.

## Good default SEO does not require merchant expertise

All eligible published merchant pages receive sound public metadata/HTML/canonical/sitemap treatment automatically, including Free. The owner enters actual business/service/product facts; Taplo derives technical output and explains material missing facts. Search Console is an optional monitoring/ownership workflow, not a prerequisite for a business page to be discoverable. No claim of guaranteed indexing, rankings, leads or instant traffic.

Studio Page → Search visibility offers a concise health view and contextual edits: page published, chosen public address, suitable title/description, public business facts, crawl/index policy, sitemap inclusion and known search status where evidence exists. Do not invent a 98/100 SEO score or label an uninspected URL Google verified.

## Property model and authority

Google distinguishes Domain properties verified through DNS from URL-prefix properties that can scope a particular protocol/host/path. [R90] Merchant ownership of their Taplo business does not grant root Search Console access for the entire Taplo domain.

| Public address | Property/control design | What the merchant must never receive |
| --- | --- | --- |
| Taplo path such as https://mytaplo.com/chapter/ | Taplo operates its domain property; optional merchant URL-prefix verification only for exact assigned subtree and validated route model | Root-domain DNS token or domain-wide performance data |
| Merchant subdomain on Taplo host | Exact host/subtree scope with separate ownership/lifecycle constraints | Parent-domain verification or wildcard access |
| Merchant-owned custom domain | Merchant retains domain ownership/property; guided DNS verification or permitted URL-prefix method | Taplo claiming exclusive ownership of the merchant's whole existing website |
| Existing website plus Taplo booking subdomain | Separate relevant properties or authorised views; canonical rules follow actual content | Assumption both sites are one property or automatic historical-data transfer |

Do not promise directory verification before testing Google's exact accepted property/method/location. Some public routes may lie outside the merchant subtree: redesign the public route tree or offer constrained reporting rather than fake a prefix that covers unrelated pages. Use trailing slash/path boundaries and parsed URLs; chapter must not match chapter-two. Verify IDN, case, encoded path and host normalisation appropriately.

## Verification workflow

1. Authorise actual owner/admin to manage merchant search settings and display the exact public scope/primary host.
2. Offer Open Search Console setup with accurate instructions. For a custom Domain property, owner follows Google's DNS method at the actual domain provider; DNS updates must not disturb email/other records.
3. Where a supported URL-prefix HTML-tag method is selected, accept only the verification token needed for the validated tenant scope. Do not allow arbitrary head HTML/scripts, parent-domain token placement or a user-selected root page.
4. Publish the validated token in the public head only at its appropriate tenant verification surface; verify raw unauthenticated response. Token storage is owner/tenant scoped and audited.
5. The owner completes Google's verification, or an explicitly authorised supported integration does so. Token saved in Studio is not equivalent to Google verification success.
6. Retain/remove tokens deliberately as ownership changes. Google's verification can be rechecked; removing a token may affect continued ownership. Do not remove other owners' valid evidence indiscriminately. [R91]

Restrict any verification-file support to Google's exact required filename/content/location and permitted scope. Never expose a generic upload-to-root tool or proxy arbitrary verification paths. Initial default is a supported token method/custom-domain DNS guidance; file-based automation can remain unavailable until its multitenant safety is proven.

## Optional Studio reporting integration

Google sign-in alone is not permission to access Search Console data. Use OAuth, least required scopes and actual property access; for read-only reports prefer supported read-only authority. Offer the user only properties they can access and verify the selected scope matches the merchant's approved host/path. Do not import every property in their Google account into this business. [R92]

States: Not connected, Authorisation needed, Property selection needed, Verification needed, Connected/no data yet, Reporting available, Access revoked, Provider error and Disconnected. Show last retrieved date and data coverage. Private report queries/URLs may reveal commercially sensitive information; tenant scopes, staff reporting grants, retention and token protection apply.

If using Taplo's own platform property to derive merchant reporting, do server-side exact merchant URL filtering and output minimisation. Never fetch a whole-domain report into the browser then hide other businesses in JavaScript. Validate Google data restrictions/report completeness and practical quotas before shipping that mode; do not advertise a native per-merchant account integration if it is actually a platform-derived report.

## Reports and status truth

Search Analytics can provide clicks/impressions/CTR/position by allowed dimensions and date ranges, but the API does not guarantee every row. Show scope, dates, source and known missing/delayed data. Zero data is not proof a page is blocked. Average position is an aggregate, not a promise of a fixed ranking for each searcher. [R93]

URL Inspection API reports the indexed version's status; it is not a live-page indexability test or an indexing-request API. Keep Published, Technically eligible, Sitemap included, Google status last checked and Observed search traffic separate. [R94] Do not add Submit to Google instantly through a general indexing API shortcut.

## Sitemap and publication lifecycle

Generate public canonical eligible business/offer/profile URLs from actual published data, with accurate significant modification dates. Exclude private/draft/preview/confirmation/token URLs and unbounded filter combinations. Domain/path ownership and sitemap location scope must match; custom domains have a valid host-specific approach. Sitemap submission is a discovery hint, not an indexing guarantee. [R95]

Logo/title/offer publication updates HTML/metadata/share data and sitemap where relevant. Handle/custom-host changes require redirect/canonical/sitemap/verification review; preserve stable IDs and customer links. Domain departure must preserve merchant ownership/export information and remove inappropriate Taplo tokens/access without promising transfer of Search Console history.

## Business facts and content

Useful authored introduction, accurate category, public area/premises facts, service/product descriptions, genuine imagery and eligible staff profiles support customer understanding. Do not fabricate an address for a mobile/home-based merchant or generate hundreds of local pages from a radius. Search descriptions can be suggested from authorised facts; price/duration/working-time import remains prohibited. Schema eligibility, actual visible facts and applicable review/rating rules still apply.

Provide a short owner checklist with direct in-context editing rather than requiring SEO vocabulary. Search visibility is distinct from Explore listing eligibility and share previews. Changing one does not silently publish private location or submit a business to Google Business Profile.

## Console, offboarding and tests

Console sees approved host/property mapping, token presence state, selected method, last safe check and redacted errors. It cannot grant external property access, read all tenant search data or move merchant DNS by improvisation. Ownership transfer/revocation reviews old tokens/OAuth/property access under explicit permission; no account is handed to a new staff member simply by editing an email.

Acceptance: root token attempt rejected; chapter/chapter-two prefix isolation; custom-domain existing website untouched; unsupported property method explained; Google token saved but unverified; revoked OAuth; no data yet; sparse/limited API rows; stale inspection result; missing sitemap URL; moved handle/domain; sensitive private URL excluded; staff reporting denied; duplicate callback; merchant exit. Exact integration schemas/quotas/permissions and live verification remain required before release.
