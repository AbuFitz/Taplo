# 96 · Quick-setup catalogue and surface rules

Working edition 1.5 · 3 November 2026 · Working defaults extending 89/92/93. This catalogue covers common setup families, not every field of every category. Full feature packets and exact command schemas remain required.

## Choose scope, not an arbitrary number of fields

Quick setup completes a small coherent outcome safely from the current task. It does not hide required information, make a regulated integration look like a toggle or override the full editor's advanced state. Prefer inline for simple facts, a focused sheet/popover for a short related task and a dedicated full workspace for complexity. One active task context; no modal cascade.

## Surface rules

On mobile, use an anchored expansion only where it remains readable; otherwise a comfortable sheet with visible close, title, scroll and keyboard-safe action. On desktop, use contextual inline space/popover for a small edit; larger editors can use a modal or work canvas. Do not force identical pixel composition across devices. Clear/Colour cap/Split tone remain merchant-popup appearance choices; Studio setup surfaces retain platform clarity instead of inheriting arbitrary merchant page backgrounds.

Keep the origin task draft independent from the saved related setting. If a service has unsaved edits while hours save, show that distinction rather than claiming the entire service is saved. Full-settings navigation carries exact tenant/resource context and safe draft state; browser Back/return is deliberate, not accidental URL behaviour.

## Quick/full consistency invariants

Unshown fields survive; server authorisation is the same; validation and money/time rules are the same; saved revision is shared; conflicts are explicit; completion derives from source records; historical agreements are unchanged; advanced override/inheritance is visible; source projections invalidate correctly. No local-only success indicator or shadow quickSetupData store may bypass the full feature.

## Data and integration boundaries

Entering a sender name does not register an SMS sender; choosing Google Calendar does not grant OAuth; saving a domain does not verify DNS; checking deposits does not authorise future card charges. Quick setup may prepare these tasks, then must hand over to the actual required external or protected operation. Preserve context on return and verify authoritative state before unlocking the capability.

## Testing and deepening order

Start with identity, working time, first offer price/duration and collection: commonly useful and traceable. Then build assignment, deposit and provider handover once dependent rules/contracts exist. Complex classes/quotes/marketing/rewards need their dedicated feature packets, not a copy of the hours editor. Evaluate quick setup by task completion, wrong settings, abandonment/recovery and later correction—not raw click count.

Every row needs eventual designed mobile/desktop states, exact command/field bindings, role matrix, data/privacy rules and acceptance cases. This catalogue makes those obligations visible; it does not imply they have all been produced today.
