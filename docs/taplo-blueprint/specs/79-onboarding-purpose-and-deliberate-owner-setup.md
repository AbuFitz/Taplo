# 79 · Onboarding purpose and deliberate owner setup

Edition 1.1 · 3 November 2026 · Supersedes earlier suggestions to use website extraction as an onboarding route or import prices. This is a proposed experience reconstruction, not a claim the live form has been redesigned.

## Recommendation

Website extraction is not required to deliver Taplo's core value. Defer it from the initial release unless observed setup difficulty demonstrates a real benefit. If offered later, place a small optional basic-content assistant in Studio, not a prominent fork in the onboarding form. The core manual setup must be excellent without it. Do not let an importer become the reason the underlying form remains confusing.

Pricing, duration, booking mode, availability, stock, payment and fulfilment are deliberate owner configuration. Do not extract, prefill, suggest from a source website, or overwrite these commercial/operational values. Showing an imported amount with a confirmation checkbox still imports the price and does not meet this direction. An independently authorised future CSV/migration project would require a separate explicit decision; it is not implied by basic content assistance.

## Two connected stages

**Onboarding establishes identity, intent and a recognisable draft.** Ask the business name, a helpful searchable category/capability suggestion, primary customer action and a recommended starting look. Optional actual logo/photo and colours help it feel theirs; no assets must also look deliberate. Category is a suggestion and may be changed. Support mixed capabilities without asking every business every operational question. Account creation follows a useful recognisable draft, subject to security requirements of the actual chosen flow.

**Studio guides the first meaningful setup task.** Take them straight to the next relevant action: add a service, add a product, create a class, or set up enquiries. The selected intention and draft survive the handover. Show the offer taking shape as they enter its name and configure its price/mode themselves. Scheduling/fulfilment/payment steps appear only as that offer needs them. Avoid landing a novice in a generic dashboard with a dozen equally important cards.

These are stages and outcomes, not a rigid identical step count for every business. A solo barber and a maker should not complete the same operational questionnaire. Keep Back, Skip where appropriate, save/resume and a clear next action. Do not require full catalogue/team/SEO/marketing setup before the first useful result.

## Information timing

| Information | When needed | Reason |
| --- | --- | --- |
| Name, useful category suggestion, primary customer goal | Early draft creation | Relevant wording, layout and next task |
| Logo/photo, colours, short introduction | Optional early choice or later Page edit | Personal attachment without a media upload gate |
| Existing website URL | Optional business link in Studio | Complement their site; not a mandatory extraction step |
| First offer name and manual price/mode | Guided offer setup in Studio | Owner understands and owns the commercial agreement |
| Duration, staff/resources, location, working time | When enabling scheduling | Correct operational commitment, not premature questionnaire |
| Variants, stock and delivery/collection | When enabling goods | Relevant commerce facts, entered deliberately |
| Public contact/location, seller facts and applicable terms | Relevant publication/transaction readiness | Clear purpose; private data does not become public by default |
| Payment verification and required account information | Before accepting payments | Correct provider flow and actual requirement |
| Team invitations and permissions | When owner adds people | Solo businesses need no empty team setup stage |
| Domains, NFC, rewards, stock imagery | Contextual optional tasks | Add value after the core path is understandable |

## Smart behaviour that earns its place

Recommend a composition that suits the authored name and actual asset choices; coordinate safe colour pairings; show only relevant fields; preserve entered content when switching looks; offer sensible capability terminology; explain inherited settings; detect missing readiness facts. Do not invent prices, durations, policies, testimonials, staff or work history. Suggested structure saves work; the owner still makes meaningful business decisions.

Keep current values visible when changing a choice and preview consequences. Price controls use the owner's fixed/from/quote/free choice where appropriate; unrelated fields collapse rather than linger disabled. Example content is distinct from authored facts and cannot become a transaction without deliberate real configuration. Preview interactions must help review what a customer will do without accidentally publishing or charging.

## Visual/form reconstruction

Use a calm single task focus, short labels and helpful defaults. On mobile, retain a useful framed phone preview at the top with controls arranged clearly below/in a suitable sheet; do not shrink it into an unreadable thumbnail or let keyboard/sticky actions obscure the active field. Frameless workspace direction does not prohibit a meaningful device frame around the preview. Desktop can show preview and scoped controls side by side. Light/dark, text enlargement, no-photo/long-name and keyboard states are designed explicitly.

The current live form requires its own actual interaction/design audit before implementation. This specification does not pretend reading prior notes equals observing the current deployment. Test whether a new owner understands the next step, can set a correct price and produces a useful draft without coaching. Measure mistakes/assistance and attachment to the result as well as time; do not optimise only for the shortest signup.
