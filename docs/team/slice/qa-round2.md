- No critical violations. Serious items:
  1. `frame-focusable-content` is new since round 1 (round 1 reported 0). Cause: the fix set tabindex -1 on an iframe whose document has focusable content. It is an intended trade-off against the Tab trap, but the spec's "full preview" alternative does not exist, so it is a real keyboard access gap.
  2. Dialog `color-contrast` is a symptom of the share sheet having no background (see below), so axe measures against the blurred overlay. Not a Studio change, but it appears in the Studio QR flow.
- Incomplete `color-contrast` (23 nodes on the page): not resolved by the tool. This is a supplement to keyboard and semantic checks, not WCAG certification.

## Other findings (not criteria)
- The Share sheet (QR dialog) is see-through: computed background `rgba(0,0,0,0)` because `bg-tp-*` tokens (`--tp-surface`, `--tp-accent`) are undefined in the dashboard scope. The page behind shows through; the title "Share Marlowe & Finch" overlaps the page and the phone frame, the Copy link and Save QR buttons are unstyled text. Screenshots `qrsheet-390.png` and `qr-1440-full.png`. The same appeared in round 1's `qr-390-1.png`, so it predates this commit, but it is visible in the QR flow.
- Share row now shows the full `http://localhost:3200/demo/p/{slug}` (not the `mytaplo.com/` address); in production this would be the real origin. One address everywhere is confirmed.
- Round-1 deviation D (preview scale 523 px at 844, 340 px at 600 versus spec ~46%, max 40%) is unchanged; criteria 1 and 2 still pass.

## Limitations
- Chromium desktop emulation only: no real phone, touch hardware, iOS Safari or software keyboard. Criterion 16 relies on `visualViewport` emulation (page-scale factor and a stubbed height), which exercises the code path but not a real keyboard.
- State seeded in localStorage (`taplo.demo.v2`, bookings store); preview failure by `route.abort` and by a never-fulfilled route; clipboard denial by a stubbed `writeText`. Success path read the clipboard back with granted permissions.
- Loading skeleton observed with CPU throttle and delayed JS; the hydration window cannot be lengthened further without changing app code, and the layout shift API under-reports (see 17).
- No participants, no user testing, no accounts, payments or external messages. Existing Playwright suites (`tests/e2e/studio-home.spec.ts`) and unit tests were not run in this pass, so there is no baseline-versus-regression comparison.
